# E2E 테스트 계획서 템플릿

`e2e-test-plan.md`(또는 사용자가 지정한 경로)를 이 구조로 작성한다. 이 계획서는 **사람이 검토·승인하는 문서**다. 셀렉터·테스트 코드는 넣지 않는다 — 그건 승인 후 Author 단계 소관이다.

작성 원칙:

- 시나리오 단계는 **산문**으로. "사용자가 무엇을 하면 무엇이 보인다" 수준. `page.click('#id')` 같은 코드는 금지.
- 기대결과는 **관찰 가능한 사실**로. "잘 동작한다"가 아니라 "한도 결과 화면에 승인 금액이 원화로 표시된다".
- 모르는 건 추측하지 말고 "오픈 질문"에 적는다.

---

## 템플릿 (이 형식을 그대로 사용)

```markdown
# E2E 테스트 계획서: <앱/기능 이름>

> 상태: 검토 대기 (Draft — 사람 검토 게이트 통과 전)
> 작성: <날짜> · 범위: <대상 영역>

## 1. 목적과 범위

- 이 계획이 지키려는 것: 잘못된 수정이 핵심 사용자 플로우를 깨뜨리지 않도록 하는 회귀 안전망.
- 대상(In scope): <어떤 영역/플로우를 다루는지>
- 비대상(Out of scope): <의도적으로 제외한 것과 그 이유 — 예: 정적 소개 페이지, 시각 회귀, 관리자 내부 화면>

## 2. Critical User Flow 목록 (우선순위 순)

| ID | 플로우 | 우선순위 | 걸리는 렌즈 | 근거 |
| --- | --- | --- | --- | --- |
| CUF-1 | <예: 대출 한도조회> | P0 | 신뢰+데이터 | <라우트/이슈/문서 근거> |
| CUF-2 | <예: 대출 신청 완료> | P0 | 매출 | <근거> |
| CUF-3 | <...> | P1 | <...> | <근거> |

> 우선순위 기준은 cuf-criteria.md 참조(매출/데이터/신뢰 × 빈도).
> 표 대신 리스트로 적어도 된다 — 검토자가 읽기 편한 쪽으로.

## 3. 플로우별 시나리오

### CUF-1: <플로우 이름> (P0)

- 왜 중요한가: <실패 시 매출/데이터/신뢰 어디에 어떻게 타격인지>
- 선행조건(Preconditions): <로그인 상태, 테스트 계정, 모킹 필요한 외부 인증/결제 등>
- 시나리오(Happy path):
  1. <진입> — 사용자가 …하면 …화면이 보인다.
  2. <입력/동의> — …을 입력/선택하면 …
  3. <분기/인증> — …
  4. <완료> — …
- 기대결과(관찰 가능):
  - <완료 화면에 무엇이 보여야 하는가 — 구체적 텍스트/상태>
- 주요 분기·엣지(테스트할 가치가 있는 것만):
  - <예: 자격 미달 시 안내 화면, 인증 실패 시 재시도>
- 탐색 메모: <playwright-cli로 둘러보며 확인한 실제 라우트·화면 전환, 막힌 지점>

### CUF-2: <...>

(같은 형식 반복)

## 4. 가정과 오픈 질문 (검토자 확인 필요)

- 가정: <예: 테스트 계정으로 본인확인을 모킹할 수 있다고 가정>
- 오픈 질문:
  - <예: 결제는 실거래 없이 sandbox로 검증 가능한가?>
  - <예: 한도 결과 화면의 정확한 성공 문구는?>

## 5. 검토 결과 (사람이 채움)

- [ ] 우선순위 동의
- [ ] 빠진 핵심 플로우 없음
- [ ] 과한 플로우 없음
- 승인자: ___  · 승인일: ___
```

---

## 채울 때 자주 막히는 부분

- **"완료"의 정의가 애매할 때**: 사용자가 그 플로우를 "성공적으로 끝냈다"고 느끼는 화면/메시지를 기준으로 잡는다. 모르면 오픈 질문으로.
- **외부 의존(결제 PG·본인확인 SDK)**: 끝까지 진행하지 말고 "선행조건"에 "모킹/sandbox 필요"로 적는다. 탐색 중 거기서 멈춘 사실도 탐색 메모에 남긴다.
- **분기를 어디까지 적나**: 깨졌을 때 매출/데이터/신뢰에 타격인 분기만. "버튼 색이 회색이 됨" 같은 건 적지 않는다.
