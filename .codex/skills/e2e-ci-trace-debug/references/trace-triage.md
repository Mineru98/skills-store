# Trace Triage 체크리스트 (CI 맥락)

SKILL.md 3단계에서 **받은 trace를 어느 유형으로 분류해 다음 단계로 넘길지** 정할 때 연다. 목적은 근본 원인을 끝까지 파는 게 아니라 — 그건 `e2e-test-healer`의 일이다 — CI 맥락에서만 필요한 **빠른 분류와 라우팅**이다.

`npx playwright show-trace <trace.zip>`로 trace viewer를 열고, 실패한 액션을 선택한 뒤 그 순간의 **DOM 스냅샷 / 스크린샷 / 네트워크 / 콘솔**을 본다. trace viewer 기능은 `playwright-cli`의 `references/tracing.md` 참조.

## 가설을 먼저, 그다음 확인

trace를 처음부터 끝까지 다 읽지 않는다. 1단계에서 뽑은 **실패 종류**(assertion / timeout / setup)로 가설을 세우고, 그 가설을 확인할 탭만 연다. 현장 전체를 훑지 말고 단서를 좁힌다.

## 실패 유형별 분류

### A. 셀렉터/UI 변경 (가장 흔함)
- 신호: `locator(...) ... waiting for` 후 timeout, DOM 스냅샷에 그 셀렉터가 **없음**, 스크린샷엔 페이지가 정상으로 보임.
- 의미: **테스트가 낡았다**. 제품은 멀쩡, 셀렉터/텍스트만 바뀜.
- 라우팅: 테스트 수정 케이스 → Healer. 새 셀렉터는 추측 말고 현재 페이지에서 role 기반으로 확인.

### B. 타이밍/대기 부족
- 신호: 같은 스펙이 로컬·재실행에선 통과(=flaky), 네트워크 탭에 늦게 끝나는 요청, `waitForTimeout` 같은 고정 대기 흔적.
- 의미: 테스트의 **대기 조건이 약함**. CI가 더 느려서 드러남.
- 라우팅: deflake/대기 강화 → Healer(+ 필요시 `e2e-test-hardener`). 단, 매번 같은 지점에서 죽으면 B가 아니라 D일 수 있다.

### C. 환경/인증/시드 데이터
- 신호: 스크린샷이 **로그인 화면·403/500 에러 페이지·빈 목록**. 네트워크에 401/403, 또는 시드 데이터 없음.
- 의미: 테스트 로직이 아니라 **CI 환경** 문제(시크릿 미주입, baseURL 오설정, 시드 누락).
- 라우팅: 테스트를 고치지 말 것. **CI/환경 설정 문제로 보고**한다. 자격 증명을 trace에서 읽어 코드에 넣지 않는다.

### D. 제품 코드 회귀 (테스트가 옳다)
- 신호: 액션은 정상 수행됐는데 **기대한 결과가 실제로 안 나옴** — 성공 토스트가 안 뜸, 잘못된 값 렌더, 콘솔에 앱 에러 스택, API가 4xx/5xx.
- 의미: 테스트는 정확히 회귀를 잡은 것. **제품 코드를 고쳐야 한다.**
- 라우팅: 테스트를 통과시키려 만지지 말 것. Healer가 "테스트 vs 제품"을 최종 판정하지만, D 신호가 명확하면 그 사실을 함께 넘긴다.

### E. 인프라/플래키 (테스트·제품 둘 다 아님)
- 신호: 브라우저 크래시, 네트워크 타임아웃이 무작위 지점, 재실행하면 다른 곳에서 실패.
- 라우팅: 먼저 재실행으로 재현성 확인(`gh run rerun <RUN_ID> --failed`). 재현 안 되면 인프라 플래키로 보고하고, 재현되면 B/D로 재분류.

## 로컬 vs CI 격차 (이 스킬 고유의 판단)

CI에서만 깨지고 로컬에선 통과하는 경우가 잦다. 이때 trace의 가치가 가장 크다 — CI 그 순간의 DOM·네트워크가 그대로 남아 있기 때문이다. 좁히는 순서:

1. trace 스크린샷이 로컬과 **시각적으로 다른가** → 다르면 환경(C)·데이터 문제 우선.
2. 네트워크 타이밍이 로컬보다 **현저히 느린가** → 타이밍(B).
3. 둘 다 같아 보이는데 결과만 다르면 → 제품 회귀(D) 또는 환경별 feature flag.

같은 셀렉터/플로우를 로컬에서 `playwright-cli`로 직접 재현해 보면 격차가 빠르게 드러난다.

## 분류 산출물

3단계를 마치면 다음을 들고 4단계(Healer 위임)로 간다:
- 로컬 `trace.zip` 절대 경로
- 실패 스펙 위치(`path/to/spec.ts:line`)와 테스트 제목
- 분류(A~E) + 한 줄 가설
- (C/E면) 테스트가 아니라 환경/인프라 문제라는 판단 근거
