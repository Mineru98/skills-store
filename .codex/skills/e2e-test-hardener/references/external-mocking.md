# B. 외부 의존성 모킹 — 호출 위치로 결정한다

SKILL.md 2단계의 세부. 발표의 원칙: **'통제할 수 있는 것만 테스트'.** 우리 코드의 분기는 진짜로 돌리되, 우리가 바꿀 수 없는 외부는 고정 응답으로 대체한다.

## 무엇이 "외부"인가 (모킹 대상 체크리스트)

우리가 코드로 바꿀 수 없고, 그대로 호출하면 느리거나 우리 테스트를 깨뜨릴 수 있는 것:

- 네이버 인증서 / 간편인증
- 홈택스·정부 연계 API
- 전자증명서 발급/검증
- 네이버앱(외부 앱) 딥링크·연동 콜백
- 결제 PG(외부 결제창)
- 외부 OAuth 제공자(카카오·구글 로그인 등)
- 환율·시세 등 시시각각 변하는 서드파티 데이터
- SMS/이메일 발송 게이트웨이

반대로, **모킹하면 안 되는 것**: 우리 자신의 API·DB·BFF의 *비즈니스 로직*. 그건 검증 대상이다. 모킹하면 테스트가 아무것도 보장하지 못한다.

## 핵심 판단: 그 외부 호출은 어디서 일어나는가?

같은 "외부 데이터"라도 호출 위치에 따라 모킹 지점이 완전히 다르다. **먼저 호출 스택을 확인**한다.

```
1) 브라우저(클라이언트)에서 fetch/XHR로 직접 호출
   → Playwright page.route 로 가로채 고정 응답을 fulfill
   → 문법: playwright-cli/references/request-mocking.md
   → 확인법: 브라우저 Network 탭(또는 playwright-cli network)에 그 요청이 보이면 클라이언트 호출

2) 서버에서 호출 (Next.js SSR / Route Handler / BFF / Server Action)
   → page.route는 못 잡는다. 요청이 브라우저를 거치지 않기 때문.
   → E2E 전용 환경변수로 그 호출 지점을 분기시켜 고정 응답을 반환
   → 확인법: Network 탭에 안 보이는데 화면에는 데이터가 그려져 있으면 서버 호출
```

이 분기를 틀리면 흔한 함정에 빠진다: **`page.route`를 걸었는데 데이터가 SSR로 이미 그려져 모킹이 무시되고, 테스트는 조용히 진짜 외부를 때린다.** 동작하는 것처럼 보여서 더 위험하다.

Next.js 엔터프라이즈 앱에서는 같은 자원이 SSR 초기 렌더로도, 클라이언트 하이드레이션 후 fetch로도 올 수 있다. 둘 다 외부를 탄다면 **두 지점 모두** 막아야 한다(env 분기 + page.route).

## 1) 클라이언트 호출 — page.route

메커니즘은 playwright-cli의 `request-mocking.md`에 전부 있다(URL 패턴, `--body`, 조건부 응답, 응답 변조, 네트워크 실패 시뮬레이션). 이 스킬에서 추가로 결정할 것:

- **무엇을 fulfill할까:** 검증할 갈래에 맞는 *최소 고정 응답*. 외부 성공 응답, 그리고 실패 갈래를 검증한다면 외부 실패 응답(타임아웃·4xx·5xx)도 케이스별로.
- **너무 넓게 막지 말 것:** `**/*`로 다 막으면 우리 API까지 모킹돼버린다. 외부 호스트/경로만 정확히 패턴팅한다.
- **테스트별로 다른 응답이 필요하면** 조건부 fulfill 또는 테스트 내 라우트 재정의를 쓴다(역시 request-mocking.md).

## 2) 서버 호출 — E2E 전용 환경변수 게이팅

서버에서 일어나는 외부 호출은 네트워크 인터셉트로 못 막으니, **코드가 E2E 모드일 때 고정 응답을 반환**하도록 분기한다.

패턴(개념): 외부 클라이언트를 감싸는 한 지점에서 환경변수를 보고 갈린다.

```ts
// 예: 서버에서 외부 인증서 검증을 호출하는 지점
export async function verifyCertificate(payload: VerifyPayload): Promise<VerifyResult> {
  if (process.env.E2E_MOCK_EXTERNAL === '1') {
    // E2E 전용 고정 응답. 진짜 외부를 때리지 않는다.
    return MOCK_CERT_RESULTS[payload.scenario ?? 'success'];
  }
  return realCertClient.verify(payload); // 운영 경로
}
```

결정 가이드:
- **게이트는 한 곳에 모은다.** 외부 어댑터/클라이언트 레이어(예: infrastructure 계층)에서만 분기하고, 비즈니스 로직 곳곳에 `if (E2E)`를 흩뿌리지 않는다. 분기가 흩어지면 운영 코드가 오염되고 검증 신뢰가 떨어진다.
- **고정 응답은 시나리오별로** 준비한다(success/expired/error). 테스트는 환경변수나 요청 헤더로 시나리오를 선택한다.
- **운영에서 절대 켜지지 않게** 한다. 이 변수는 E2E 실행 환경에서만 주입한다(테스트 러너 env, CI의 테스트 잡 한정). 운영 빌드/런타임에는 존재하지 않거나 강제로 꺼져야 한다.
- env 파일 전략은 프로젝트의 AGENTS.md 또는 `.codex/rules/**`에 있는 env/build 규칙을 따른다. 비밀이 아닌 테스트 플래그라도 `NEXT_PUBLIC_*`로 노출하지 않는다(서버 전용이면 클라이언트 번들에 셀 이유가 없다).

## 모킹이 진짜 동작하는지 확인

모킹은 "걸었다"가 아니라 "외부를 안 탔다"로 검증해야 한다:
- 클라이언트: `playwright-cli network`(또는 트레이싱)로 외부 호스트로 나간 요청이 없는지 본다.
- 서버: E2E 모드에서 외부 클라이언트가 호출되지 않았음을(로그/스파이/응답 일관성) 확인. 외부가 다운돼도 테스트가 그린이면 제대로 고정된 것.

## 모킹 vs 진짜 호출 — 마지막 점검

- 우리 비즈니스 로직인가? → 진짜로 돌린다.
- 통제 불가능한 외부인가? → 모킹/고정.
- 외부 자체의 계약을 검증하려는 건가? → 그건 E2E가 아니라 별도 계약 테스트의 일이다. E2E에 섞지 않는다.
