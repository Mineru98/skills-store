# 백엔드 이슈 대조 분석

## 1. 증상에서 코드로 좁히기

```bash
# 에러 메시지 원문이 가장 강한 단서
rg -n "COUPON_EXPIRED" -g '!node_modules'
# 엔드포인트 경로로 라우터/핸들러 찾기
rg -n "'/api/orders'|\"/api/orders\"|@(Get|Post)\(" -g '!node_modules'
# 느린 쿼리는 테이블명으로
rg -n "from orders|FROM orders" -g '*.{sql,ts,py,go,java,kt}'
```

라우터 → 컨트롤러/핸들러 → 서비스 → 리포지토리/쿼리 → 스키마 순으로 따라간다.

## 2. 채워야 할 조사 항목

```text
엔드포인트     라우트 정의 위치와 핸들러 (path:line)
호출 체인      핸들러 → 서비스 → 저장소까지의 함수 경로
쿼리          실제 실행되는 SQL, 인덱스 유무, N+1 여부
트랜잭션      경계와 격리 수준, 재시도 정책
외부 의존      다른 서비스·큐·캐시 호출과 타임아웃 설정
데이터 상태    문제가 되는 실제 레코드 조건
계약          응답 스키마, 이 변경이 클라이언트에 주는 영향
기존 테스트    단위/통합 테스트, 벤치마크 스크립트 유무
```

## 3. 자주 나오는 원인 유형

```text
증상                    먼저 볼 곳
----------------------  ----------------------------------------
목록 API 가 느림         N+1, 인덱스 미사용, 불필요한 count, 페이지네이션 없음
간헐적 타임아웃          커넥션 풀 크기, 외부 호출 타임아웃 미설정, 락 경합
중복 생성               멱등키 없음, 유니크 제약 없음, 재시도와 조합
정합성 깨짐             트랜잭션 경계 밖 쓰기, 이벤트 순서 보장 없음
메모리 증가             전체 로드 후 필터링, 스트리밍 미사용, 캐시 무한 증가
500 에러                입력 검증 누락, null 처리, 외부 응답 스키마 변화
```

## 4. 성능 이슈면 기준선을 먼저 잡는다

착수 시점에 before 를 측정해 두는 편이 훨씬 정확하다. 지금 잡아 둔다.

```bash
# 프로젝트에 있는 벤치/부하 스크립트를 먼저 찾는다
rg -n "bench|k6|locust|autocannon|oha" package.json Makefile 2>/dev/null

# 없으면 단발 측정이라도 남긴다
mkdir -p .issue/59
oha -z 30s -c 50 http://localhost:8080/api/orders | tee .issue/59/baseline.txt
psql -c 'EXPLAIN (ANALYZE, BUFFERS) SELECT ...' | tee -a .issue/59/baseline.txt
```

측정 조건(데이터셋, 동시성, 머신, 커밋 해시)을 함께 기록한다. 조건이 다르면 비교가 의미 없다.
