# E2E 운영·작성 규칙 SSOT 가이드

> 단계 2 의 깊이 문서. 이 문서가 만들 산출물은 보통 `e2e/CONVENTIONS.md` 또는 `e2e/AGENTS.md` 다. **테스트 전략의 단일 출처(Single Source of Truth)**.

## AGENTS.md 와 무엇이 다른가

- AGENTS.md = 코드베이스 지도(서비스가 뭔지, 어디에 뭐가 있는지). 모든 작업이 읽는다.
- SSOT = **E2E 만의 운영 규칙 + 의사결정 로그**. 테스트를 짜고 굴릴 때만 읽는다.

둘을 분리하는 이유: 섞으면 문서가 비대해져 아무도 끝까지 안 읽고, 규칙과 지도가 함께 썩는다. 짧고 살아있게 유지하려면 역할을 나눈다.

## 반드시 답해야 할 질문

에이전트가 사람에게 다시 묻지 않아도 되도록, 아래를 **명시적으로** 적는다. 모르면 사람에게 인터뷰해서 채운다 — 이 인터뷰가 단계 2 의 핵심 작업이다.

### A. 실행 환경
- 어떤 명령으로 테스트를 돌리나(`yarn e2e`, `npx playwright test` 등)?
- `baseURL` 은 무엇으로 결정되나? **환경변수명**과 기본값을 적는다. (하드코딩 금지가 규칙이다)
- 헤드리스/헤디드, 브라우저, 병렬도, 리트라이 정책.
- CI 에서는 어떻게 다른가(다른 baseURL, 다른 토큰 주입 방식)?

### B. 인증 시나리오  ← "우리만 아는 맥락" 1
- 테스트는 어떻게 인증하나? **로그인 폼 자동화가 아니라** 서버 세션 함수(예: `getServerState()`)를 쓰는가? 그렇다면 그 함수의 이름·위치·필요한 입력을 적는다.
- 역할별(admin/user 등) storageState 가 몇 개이고 각 파일 경로는?
- 토큰/세션은 어디서 오나(테스트 계정, 시크릿 주입)?

### C. 만료 & 에러 신호  ← "우리만 아는 맥락" 2
- 인증 만료를 어떻게 알아채나? **특정 종료 코드나 에러**가 "버그"가 아니라 "세션 만료" 신호인 경우를 적는다.
  - 예시 표현: "`code 90` 으로 테스트가 죽으면 인증 만료다. setup 프로젝트를 다시 실행해 storageState 를 갱신하라. 테스트 로직을 의심하지 마라."
- 이 항목이 없으면 에이전트는 만료를 진짜 버그로 오인해 멀쩡한 테스트를 망가뜨린다.

### D. 테스트 범위 — 무엇을 하고 무엇을 안 하나  ← "우리만 아는 맥락" 3
- E2E 로 **커버하는** 영역(핵심 결제/가입/조회 등).
- E2E 로 **의도적으로 안 하는** 영역과 **그 이유**(예: "외부 PG 결제 콜백은 mock 으로만 — 실결제는 비용/불안정", "관리자 일괄삭제는 데이터 파괴라 제외").
- 단위/통합과의 경계: 어디까지 E2E, 어디부터 다른 레벨인가.

### E. 작성 컨벤션
- 셀렉터 정책(role 기반 우선, `data-testid` 규약), 파일/디렉토리 위치, 네이밍.
- 이 저장소의 `naming-conventions.md`·`testing.md` 와 충돌하지 않게 맞춘다.

## 의사결정 로그 (Decision Record)

SSOT 의 차별점은 **과거 결정을 박제**한다는 것이다. 결정 로그가 있으면 에이전트가 이미 기각된 접근을 다시 들고 오지 않는다. append-only 로 쌓는다(지우지 말고 `상태: 폐기` 로 표시).

포맷:

```markdown
### DR-001 인증은 서버 세션 함수로 한다
- 날짜: 2026-06-15
- 결정: 로그인 폼 자동화 대신 `getServerState(role)` 로 세션을 만들어 storageState 에 저장한다.
- 이유: 폼 자동화는 느리고 UI 변경에 자주 깨진다. 서버 함수는 빠르고 안정적.
- 영향: 모든 테스트는 setup 프로젝트가 만든 storageState 를 로드한다.
- 상태: 채택
```

```markdown
### DR-002 외부 PG 실결제는 E2E 에서 제외
- 결정: 결제 콜백은 라우트 mock 으로 검증, 실 PG 호출 안 함.
- 이유: 실결제는 비용 발생 + 외부 의존으로 플레이키.
- 상태: 채택
```

최소 3개의 DR 로 시작한다: (1) 인증 방식, (2) 환경/baseURL 결정, (3) 의도적으로 제외한 영역 1개.

## 골격 템플릿

```markdown
# E2E 운영·작성 규칙 (SSOT)

## 실행
- 명령: `<...>`
- baseURL: `<ENV_VAR>` (기본 `<...>`)
- 브라우저/병렬/리트라이: ...
- CI 차이: ...

## 인증
- 방식: <getServerState(role) 위치/입력 | ...>
- 역할별 storageState: admin → `<경로>`, user → `<경로>`
- 만료 신호: <code/에러> = 만료 → 대응: setup 재실행

## 테스트 범위
- 커버: ...
- 제외(+이유): ...

## 작성 컨벤션
- 셀렉터: role 우선 / data-testid 규약 ...
- 위치/네이밍: ...

## 의사결정 로그
### DR-001 ...
### DR-002 ...
```

## 안티패턴

- "베스트 프랙티스를 따른다" 같은 빈 문장. 구체값(함수명·코드·경로·이유)이 없으면 맥락 전달 0.
- 인증/만료/범위 중 하나라도 비우는 것 — 이 셋이 에이전트가 가장 많이 헛다리 짚는 지점이다.
- AGENTS.md 내용 복붙. 지도는 AGENTS.md, 규칙·결정은 여기. 링크로 연결한다.
