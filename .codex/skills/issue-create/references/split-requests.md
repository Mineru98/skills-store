# 요청 분해

한 메시지에는 기능 추가, 버그 수정, 삭제, 문서 변경이 섞일 수 있다. 분해 목표는 문장 수를 세는 것이 아니라 **독립적으로 구현·검증·되돌릴 수 있는 작업 경계**를 찾는 것이다.

**이슈 하나 = 워크트리 하나 = PR 하나**가 뒤 단계의 전제다. 독립 작업을 뭉치면 증거와 되돌리기 단위가 흐려지고, 강하게 결합된 작업을 억지로 떼면 어느 이슈도 단독으로 완료되지 않는다.

## 판정 순서

아래 순서를 건너뛰지 않는다.

```text
1. 원자 요구사항 후보 추출
2. 후보 쌍마다 강결합 신호 판정
3. 강결합된 후보를 한 그룹으로 묶기
4. 그룹끼리 독립성 확인
5. 5개 상한 처리
6. 분할안과 근거 제시
```

## 1. 원자 요구사항 후보 추출

요청을 먼저 **검증 가능한 변화** 단위로 펼친다. 사용자가 "나눠 달라"고 말하지 않은
복합 요청도 이 단계를 생략하지 않는다. 접속사나 문장 수만으로 자르지 않는다.

각 후보는 다음 형식으로 메모한다.

```text
R1  대상 + 변화/증상 + 완료 신호
R2  대상 + 변화/증상 + 완료 신호
```

다음 표현도 별도 후보가 될 수 있다.

- `그리고`, `또`, `겸사겸사`, 쉼표 뒤에 이어진 다른 대상
- 증상 설명 뒤에 숨어 있는 수정 요청
- 사용자가 지정한 구현 방법과 그 방법으로 달성하려는 별도 결과
- 삭제·문서·설정처럼 짧게 덧붙인 요청

설명, 배경, 제약, 재현 조건은 그 자체로 변화가 아니면 후보로 세지 않는다.
`<이벤트> 발생 시 <알림을 보낸다>`처럼 앞부분이 뒤 행동의 조건이면 둘을 한 후보로 둔다. 조건절과 행동을 각각 요구사항으로 세지 않는다.

## 2. 강결합 판정

후보 두 개 사이에 아래 신호가 **하나라도 분명하면** 같은 이슈 그룹으로 묶는다.

```text
계약 결합       API/스키마를 바꾸고 같은 요청에서 소비 UI·클라이언트도 바꿔야 함
완료 결합       둘 중 하나만 끝나면 사용자 가치나 완료 기준이 성립하지 않음
원인 결합       같은 근본 원인과 같은 수정 지점을 고치는 여러 증상
배포 결합       따로 배포하면 호환성 오류나 데이터 손상이 생김
마이그레이션   데이터 변환과 새 데이터를 읽는 코드가 함께 전환되어야 함
흐름 결합       하나의 사용자 흐름을 완성하는 생산자와 소비자
되돌리기 결합   한쪽만 되돌리면 시스템이 깨짐
```

단순히 같은 화면, 같은 저장소, 같은 산업, 같은 라벨이라는 이유만으로 묶지 않는다. 선후 관계가 있어도 첫 작업이 독립 가치를 가지며 별도 배포·검증할 수 있으면 별도 이슈로 둘 수 있다.

같은 보고서를 다뤄도 조회 지연 수정과 CSV 내보내기 추가처럼 완료 기준·배포·되돌리기가 다른 작업은 별도 이슈다.

## 3. 그룹 만들기

강결합 관계를 선으로 보고 연결된 후보를 한 그룹으로 묶는다.

```text
R1 ─ R2    R3    R4

→ 이슈 A: R1 + R2
  이슈 B: R3
  이슈 C: R4
```

이 절차가 부분 결합을 보존한다. 요청 전체를 한 이슈로 만들거나 모든 문장을 각각 떼는 이분법을 쓰지 않는다.

## 3-1. fan-out과 fan-in 관계 기록

그룹 사이의 관계를 분할안부터 명시한다.

```text
fan-out  네 독립성 질문이 모두 예인 그룹들. 각각 별도 이슈·PR·검증·취소·되돌리기 단위다.
fan-in   하나의 완료 기준을 만들기 위해 계약·배포·되돌리기 결합으로 함께 끝나야 하는 후보 묶음이다.
```

각 그룹에는 다음 두 줄을 기록한다.

```text
범위      이 이슈가 맡는 원자 후보와 제외하는 후보
관계 근거 fan-out: 네 독립성 질문의 근거 | fan-in: 결합 신호와 단독 완료 불가 사유
```

이 기록은 분할안, 이슈 초안의 영향 범위, `--request-file` 원본 요청 기록에 같은 뜻으로 남긴다.
형제 이슈 번호를 미리 만들지 않으며, 근거 없는 의존 관계를 추가하지 않는다.

## 4. 그룹 간 독립성 확인

만든 그룹끼리는 다음 핵심 질문을 확인한다.

```text
1. 별도 PR로 머지·배포해도 의미가 있는가
2. 완료 기준을 따로 검증할 수 있는가
3. 한 그룹을 취소해도 나머지가 성립하는가
4. 별도로 되돌려도 다른 그룹이 깨지지 않는가
```

네 질문이 모두 `예`면 별도 이슈다. 하나라도 `아니오`면 강결합 신호를 다시 찾아 그룹을 합친다.

라벨 차이(`bug` / `enhancement` / `documentation` / `chore`)는 **보조 신호**다. 라벨이 다르면 독립 가능성을 다시 확인하지만, 라벨이 같다는 이유로 독립 작업을 합치지 않는다.

## 그룹 라벨 판정

라벨은 동사가 아니라 사용자의 의도로 고른다.

```text
bug             기존 기대 동작이 틀림: 중복·누락·초기화·오류·지연·잘못된 값
enhancement     없던 기능이나 계약을 추가: 필터·필드·내보내기·알림
documentation   코드 동작이 아니라 문서 내용을 추가·갱신
chore           사용자 기능보다 정리·운영에 가까움: 삭제·마이그레이션·설정·의존성
```

`개선`이라는 단어가 있어도 기존 동작의 결함을 바로잡으면 `bug`다. 결합 그룹은 그룹의 공통 사용자 의도를 대표하는 라벨 하나를 고른다.

## 판정 기록

내부 판단은 다음 모양으로 정리한 뒤 사용자에게는 제목·요약·예상 라벨만 보여준다.

```text
원자 후보   R1, R2, R3 (분할 명시 여부와 무관하게 모두 추출)
fan-in      R1-R2: API/UI 계약, 어느 한쪽만으로 완료 기준 불가
fan-out     {R1,R2}와 {R3}: 별도 배포·검증·취소·되돌리기 가능
범위        A=R1,R2 / B=R3
결론        2개 이슈
확신도      높음 | 중간 | 낮음
예외        제품 결정이 필요한 모호한 경계
```

확신도가 낮고 분할 수가 달라질 수 있으면 승인 질문에서 경계를 한 줄 설명한다. 근거 없이 숫자만 제시하지 않는다.

## 예시

### 라벨이 같아도 분리

```text
"대시보드에 기간 필터를 넣고 사용자 초대 알림도 추가해줘"

→ 대시보드 기간 필터 추가       enhancement
  사용자 초대 알림 추가          enhancement

별도 배포·검증·취소가 가능하므로 같은 라벨이어도 2개다.
```

### 계약으로 결합

```text
"API 응답에 createdAt을 추가하고 목록에 표시해줘"

→ 이슈 1개
  - API 응답에 createdAt 추가
  - 목록에서 createdAt 표시

생산자와 소비자가 같은 계약을 완성하므로 하나만 끝내면 사용자 가치가 없다.
```

### 부분 결합

```text
"주문 API에 배송 상태를 추가해서 목록에 보여주고, 오래된 export 스크립트도 지워줘"

→ 이슈 A: 배송 상태 API + 목록 표시   enhancement
  이슈 B: 레거시 export 제거          chore
```

### 같은 근본 원인

```text
"모바일에서 로그인 버튼이 잘리고 태블릿에서는 라벨이 겹쳐"

같은 로그인 폼 반응형 규칙과 완료 기준을 고치는 증상이면 이슈 1개 + 체크리스트다.
코드 대조 전에는 원인이 다를 수도 있어 확신도를 낮추고 사용자에게 경계를 알린다.
```

## 5개 상한

등록 가능한 분할안은 **최대 5개**다. 독립 그룹이 6개 이상이면 그대로 등록하지 않는다.

```text
질문: 독립 작업 7건을 찾았습니다. 한 번에 등록할 수 있는 상한은 5건입니다.
- 관련된 범위를 묶어 3~5건으로 조정 (권장)  → 억지 결합이 아니라 사용자 범위 결정으로 묶음
- 지금 급한 5건만 선택                       → 나머지는 원본 요청에 남기고 등록하지 않음
- 등록 취소
```

사용자가 범위를 묶으면 새 그룹에 공통 완료 기준이 생기는지 다시 확인한다. 단지 상한을 맞추려고 무관한 작업을 임의로 합치지 않는다.

## 분할안 승인

작업이 하나뿐이면 분할안 승인을 건너뛰고 초안으로 간다. 여러 그룹이면 제목, 한 줄 요약, 예상 라벨과 필요한 경계 근거만 보여준다. 본문은 아직 쓰지 않는다.

```text
승인      이 구성으로 초안 작성
병합      어느 그룹을 왜 합칠지 받아 다시 판정
분리      어느 그룹의 경계를 나눌지 받아 다시 판정
취소      등록하지 않고 종료
```

초안은 승인된 항목마다 `issue-draft.md` 형식으로 작성해 전문을 한 번에 보여주고 다시 승인받는다.

## 항목별 처리

분할안이 확정되면 항목마다 중복 검사, 작업 성격 판정, 초안 작성을 따로 수행한다.

```text
중복 검사   node <skill>/scripts/issue-create.mjs search "<항목 키워드>"
성격 판정   frontend / backend / both / neither
초안 작성   references/issue-draft.md
```

중복인 항목만 빼고 나머지는 계속한다. 분해된 이슈의 `--request-file`에는 원본 요청 전문과 이 이슈가 맡는 범위를 함께 적는다. 등록 뒤 본문을 고쳐 형제 번호를 넣지는 않는다.

## 실패하기 쉬운 패턴

- 접속사 개수만 세어 분리
- 라벨이 같다는 이유로 독립 작업을 병합
- 같은 화면이라는 이유만으로 모든 증상을 병합
- 선후 관계가 있다는 이유만으로 독립 배포 가능한 기반 작업까지 병합
- 요청 전체를 단일/전체 분리 중 하나로만 결정
- 5개를 넘는 항목을 승인 없이 그대로 등록
- 배경·제약·재현 조건을 새로운 요구사항으로 오인
