# Diagnosis Playbook — 증상에서 trace의 어느 단서로

trace는 사건 현장 전체다. 한 번에 다 읽으면 신호가 묻힌다. **증상을 먼저 분류하고**, 그 증상을 설명할 수 있는 단서만 trace에서 꺼내 본다(개발자가 devtools에서 필요한 탭만 여는 것과 같다).

trace를 여는 방법 자체(`tracing-start/stop`, trace zip 안 탐색)는 `playwright-cli` 스킬의 `references/tracing.md`를 따른다. 이 파일은 "무엇을 볼지"만 다룬다.

## 증상 → trace 단서 매핑

아래는 고정폭 표다(Markdown 표 금지 규칙 준수).

```
증상 (실패 메시지/관찰)                         먼저 볼 trace 단서                         확인할 질문
---------------------------------------------  ----------------------------------------  ---------------------------------------------
locator timeout / element not found            실패 직전 단계의 DOM 스냅샷 + 스크린샷       요소가 정말 없었나? 가려졌나? 아직 안 떴나? 셀렉터가 바뀐 UI와 안 맞나?
클릭은 됐는데 다음 단계가 실패                  단계별 스크린샷(클릭 직후)                  클릭이 의도한 화면 전환을 일으켰나? 모달/토스트가 막았나?
페이지가 비어있다 / 하얀 화면                   콘솔 로그 + 에러 스택                       런타임 JS 예외가 났나? 번들/하이드레이션 에러인가?
데이터가 안 보인다 / 빈 목록                    네트워크 탭(해당 API 요청)                  그 요청이 200인가? 응답 바디가 기대 형태인가? 호출 자체가 일어났나?
401/403로 튕김 / 로그인 화면으로 감             네트워크(인증 요청) + 스토리지              세션/토큰이 주입됐나? 인증 픽스처가 동작했나?
간헐적 실패(돌릴 때마다 다름)                   타이밍 + 네트워크 경합                      대기 없이 빠른 단언인가? 응답 순서에 의존하나? 애니메이션/리다이렉트 경합인가?
단언 값 불일치(expected X, got Y)              실패 단계 DOM + 직전 네트워크 응답           UI에 진짜 Y가 떠 있었나(테스트가 틀림)? 아니면 데이터가 틀려 Y가 됐나(코드가 깨짐)?
네비게이션 timeout                              네트워크 + 단계 스크린샷                    리다이렉트 루프인가? 느린 응답인가? URL 패턴 가정이 틀렸나?
```

마지막 행("단언 값 불일치")이 특히 중요하다. 같은 증상이 **테스트 결함**일 수도, **제품 회귀**일 수도 있다 — 그래서 trace의 DOM(실제로 뭐가 떴는지)과 네트워크(데이터가 맞았는지)를 함께 봐야 갈린다. 판정은 `decision-test-vs-code.md`로 이어진다.

## trace를 읽을 때의 순서

1. **실패 단계를 먼저 찾는다.** 어느 액션에서 멈췄는지부터. 그 직전·직후 스냅샷이 가장 정보 밀도가 높다.
2. **그 시점의 화면을 본다.** 기대한 상태였나? "내가 클릭하려는 버튼이 화면에 있긴 했나?"
3. **화면이 이상하면 원인을 한 단계 거슬러 올라간다.** 네트워크(데이터가 안 왔나)인지 콘솔(예외가 났나)인지.
4. **여기서 멈춘다.** 가설이 서면 trace를 더 헤집지 말고 코드/diff 대조로 넘어간다. trace는 "어디서·무엇이" 를 주고, "왜"는 코드가 준다.

## Flaky(간헐 실패) 진단

한 번 돌려 통과해도 해결이 아니다. 같은 스펙을 여러 번 돌려 **재현율**을 본다(레시피: `loop-recipes.md`의 반복 실행).

flaky의 흔한 뿌리와, 어느 단서가 그걸 드러내는지:

```
flaky 원인                              trace에서 보이는 신호                    고치는 방향(테스트 쪽)
-------------------------------------  --------------------------------------  ------------------------------------------
임의 sleep / 대기 부족                  실패 회차에만 액션이 화면 준비 전 실행    명시적 대기(요소/상태/응답 대기)로 교체
네트워크 응답 순서 의존                  요청 완료 순서가 회차마다 다름            특정 응답을 명시적으로 기다리거나 mock
애니메이션/트랜지션 경합                 클릭 시 요소가 이동 중                    애니메이션 종료/안정 상태 대기
테스트 간 상태 누수                      이전 테스트 잔여 데이터가 DOM/스토리지에  픽스처/스토리지 격리, beforeEach 정리
실제 시간/날짜 의존                      특정 시각대에만 실패                      시간 고정(clock mocking)
```

flaky가 **테스트의 비결정성**이 아니라 **제품의 race condition**일 수도 있다. 응답 순서나 동시성에 따라 UI가 실제로 깨진다면 그건 제품 버그다 — `decision-test-vs-code.md`의 판정을 따른다. flaky라고 무조건 테스트만 손보면 진짜 race를 숨길 수 있다.

## 막혔을 때

- trace에 단서가 안 보이면, 한 단계 더 일찍부터 trace를 켜서 다시 돌린다(실패 직전이 아니라 흐름 전체).
- 그래도 모호하면 가설을 두세 개로 좁혀 각각 무엇을 보면 갈리는지 적고, 사람에게 증거와 함께 묻는다.
