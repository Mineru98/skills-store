# 판정: 테스트가 틀렸나, 제품 코드가 깨졌나

이것이 Healer의 가장 중요한 판단이다. 잘못 판정하면 둘 중 하나가 일어난다.

- 제품 회귀인데 테스트를 비틀어 통과시킨다 → **버그를 출시하고 테스트로 덮어 숨긴다**. 최악.
- 테스트가 낡았을 뿐인데 멀쩡한 제품 코드를 바꾼다 → **새 버그를 만든다**.

그래서 고치기 **전에** 어느 쪽인지 증거로 정한다. trace의 "무엇이 일어났나"와 코드/diff의 "왜"를 삼각측량한다.

## 세 소스를 나란히

1. **테스트 코드** — 무엇을 기대하나(셀렉터, 단언, 대기, 픽스처/가정).
2. **제품 코드** — 테스트가 부르는 화면/훅/API가 실제로 무슨 일을 하나.
3. **git diff** — 마지막으로 무엇이 바뀌었나. `git log`/`git diff`로 깨짐의 시점을 좁힌다. 테스트가 며칠 전엔 통과했다면 그 사이 diff에 답이 있다.

## "제품 코드가 깨졌다(회귀)" 쪽 신호

이쪽이면 **제품 코드를 고치고 테스트는 보존**한다.

- trace의 DOM/스크린샷에 **실제로 잘못된 화면**이 떠 있다(버튼이 사라짐, 값이 틀림, 빈 목록).
- 네트워크 탭에 **4xx/5xx**, 또는 응답 바디가 계약과 다름 — 그런데 테스트는 그 계약을 올바르게 기대하고 있었다.
- 콘솔에 **런타임 예외/스택**이 찍혀 화면이 안 그려졌다.
- git diff가 **제품 코드(컴포넌트/훅/서비스)** 를 건드렸고, 그 변경이 trace의 증상과 인과로 이어진다.
- 테스트는 안 바뀌었는데 갑자기 깨졌다(특히 제품 코드 머지 직후).
- 사용자 관점에서 **실제로 기능이 망가졌다** — 단언이 잡은 게 진짜 결함이다.

> 신호: "테스트가 옳게 기대했는데 제품이 그걸 못 지켰다." 이때 단언을 약화시키면 안 된다. 단언이 제 일을 한 것이다.

## "테스트가 낡았다/틀렸다" 쪽 신호

이쪽이면 **테스트를 고치고 제품 코드는 보존**한다.

- 제품은 **의도대로 동작**한다(화면이 정상, 데이터 맞음, 네트워크 200). 단지 테스트의 가정이 현재 UI와 안 맞는다.
- git diff가 **UI를 의도적으로 변경**했고(라벨/구조/플로우 변경), 테스트가 그 변경을 안 따라왔다 — 셀렉터/단언이 옛 UI를 가리킨다.
- 실패가 **타이밍/순서**에서 온다(대기 부족, sleep 의존, 응답 순서 가정) — 제품은 멀쩡한데 테스트가 비결정적.
- 단언이 **너무 빡빡하거나**(예: 동적 텍스트를 정확 일치로) 환경 의존적(고정 날짜·로캘)이다.
- 픽스처/시드 데이터가 낡아 사전 상태가 안 맞는다.

> 신호: "제품은 올바른데 테스트가 현실과 어긋났다." 이때는 안정적인 셀렉터·명시적 대기·맞는 픽스처로 테스트를 현실에 맞춘다 — 단, 무엇을 검증하는지(테스트의 의도)는 보존한다.

## "모호하다" — 멈추고 물어본다

다음이면 혼자 결론 내지 말고 증거와 함께 사람에게 확인받는다.

- 제품 변경이 **의도된 사양 변경인지 회귀인지** 코드만으로 알 수 없다(예: 버튼 라벨이 바뀐 게 맞는 변경인지 사고인지).
- trace·코드·diff가 **상충하는 그림**을 준다.
- 고치려면 **제품 동작에 대한 제품 결정**이 필요하다(에이전트가 임의로 내릴 사안이 아님).

이때 보고에 담을 것: trace에서 본 증상, 관련 diff, 후보 원인 2개와 각각이 맞다면 어디를 고칠지. 사람이 한 번에 판단하도록.

## 사례

```
사례 A — 회귀
증상: 결제 버튼 클릭 후 단언 실패(주문번호 미표시).
trace: 클릭은 됨. 네트워크에 POST /orders 가 500. 콘솔에 서버 에러.
diff: 직전에 infrastructure/api/order/services.ts 의 payload 키가 바뀜.
판정 → 제품 회귀. services.ts 를 고친다. 테스트 단언은 그대로 둔다(옳았다).

사례 B — 낡은 테스트
증상: getByRole('button', { name: '제출' }) timeout.
trace: 화면은 정상. 버튼 라벨이 '결제하기'로 보임. 네트워크/콘솔 깨끗.
diff: presentation 에서 의도적으로 버튼 문구를 '제출'→'결제하기'로 변경(기획 반영).
판정 → 테스트가 낡음. 셀렉터를 새 라벨로 고친다. 제품 코드는 안 건드린다.

사례 C — 모호
증상: 단언 실패(목록에 3개 기대, 2개).
trace: 화면에 2개만, 네트워크는 200 + 응답에도 2개.
diff: 제품과 테스트 둘 다 최근에 바뀜. 3개가 맞는 기대인지 2개가 맞는지 불명.
판정 → 멈춤. "기대 건수가 3이 맞나 2가 맞나?" 를 증거와 함께 사람에게 확인.
```

## 고친 뒤

- 제품 코드를 고쳤다면, 가능하면 이 회귀를 못 빠져나가게 **단언을 강화**한다(다음에 같은 깨짐을 잡도록).
- 테스트를 고쳤다면, **여전히 의미 있는 걸 검증**하는지 확인한다 — 통과시키려고 검증을 비운 게 아니어야 한다.
- 어느 쪽이든 **왜 그게 근본 원인이었는지 한 줄**을 남긴다. 검증·리뷰·미래의 자신을 위한 기록이다.
