# 워크트리 인벤토리와 해결 판정

## 1. 수집

```bash
node <skill>/scripts/issue-merge.mjs inventory
```

아래 셋은 자동으로 빠진다. 물어보지 않는다.

- 기본 브랜치의 주 체크아웃
- 이 스킬이 만든 `.issue/merge/**` 보조 트리
- **기본 브랜치보다 앞선 커밋이 없는 워크트리** — 합칠 변경이 없으므로 판단할 것도 없다

### 출력 필드

```text
count           merge 후보 수
worktrees       후보 목록
excludedCount   자동으로 제외된 수
excluded        제외 목록 — { path, branch, reason }
```

후보 하나하나는 이렇게 생겼다.

```text
path            워크트리 경로
branch          브랜치 이름
issue           브랜치에서 추론한 이슈 번호 (null 이면 연결 불명)
issueState      OPEN / CLOSED
pr              { number, state, isDraft, mergeable } 또는 null
checks          pass / fail / pending / none
evidence        { dir, before, after, report }
ahead           기본 브랜치 대비 앞선 커밋 수
changedFiles    기본 브랜치와의 diff 파일 목록
overlapsWith    같은 파일을 건드린 다른 브랜치들
```

### 커밋 0개 워크트리는 왜 자동으로 빼는가

`ahead` 가 `0` 이면 기본 브랜치에 없는 커밋이 하나도 없다는 뜻이다. merge 해도 아무 변화가 없으니 후보가 될 수 없다. 세션 도구가 만들어 두고 쓰지 않은 트리, 이미 정리된 prunable 트리, 방금 만들고 아직 손대지 않은 트리가 여기 해당한다.

**`ahead` 가 `null` 인 것은 다르다.** 조회에 실패했다는 뜻이지 "0 개"가 아니다. 모르는 것을 제외하지 않으므로 후보로 남고, 아래 판정 단계에서 사람이 본다.

제외한 목록은 버리지 않고 `excluded` 로 남는다. 회차 보고에 한 줄로 남겨 무엇을 걸렀는지 드러낸다.

```text
제외   worktree-cc-20260726-044434  기본 브랜치보다 앞선 커밋이 없음
```

### issue 가 null 인 경우

여기까지 남았다는 것은 **커밋은 있는데 이슈를 못 찾았다**는 뜻이다. 브랜치 이름에 이슈 번호가 없거나 형식이 맞지 않는다. 숫자 앞은 `/` 나 `_` 여야 인식된다 — `fix/59-login` 은 되고 `fix-59-login` 은 안 된다.

이런 워크트리는 **통합 대상에서 제외하되 사용자에게 묻는다.** 실제 작업이 들어 있으므로 조용히 버리면 안 된다. 목록을 보여주고 이슈 번호를 알려줄지, 이번에는 건너뛸지 묻는다. 추측으로 이슈를 붙이지 않는다.

```text
질문   issue-merge 2단계(워크트리↔이슈 매핑)입니다.
       아래 워크트리는 커밋은 있는데 이슈를 찾지 못했습니다. 어떻게 할까요?
```

## 2. 이슈 내용 확인

후보마다 이슈 본문을 실제로 읽는다. 제목만 보고 판단하지 않는다.

```bash
gh issue view <번호> --json number,title,state,body,labels,comments
```

특히 **완료 기준**을 뽑아낸다. 3단계 판정의 기준이 된다. 완료 기준이 본문에 없으면 코멘트에서 찾고, 그래도 없으면 그 사실을 기록한다(판정을 못 한다는 뜻이다).

## 3. 해결 여부 판정

**증거로만 판정한다.** 다음은 근거가 아니다.

- 커밋 메시지에 "이슈 해결"이라고 쓰여 있음
- PR 제목이 이슈 제목과 같음
- 브랜치가 존재함

근거가 되는 것은 이것뿐이다.

```text
1. 이슈의 완료 기준 각 항목에 대응하는 증거 파일이 있는가
   - 프론트엔드: before/after webp 가 짝을 이루고, after 에 변경 구간 박스가 있는가
   - 백엔드: before/after 측정 원본이 같은 조건으로 재현됐는가
2. 이슈에 그 증거가 렌더링된 코멘트가 실제로 달려 있는가
3. PR 이 있고 CI 가 통과했는가
```

판정 결과를 표로 정리해 사용자에게 보여준다.

```text
이슈   브랜치                  증거        PR    CI     판정
----  ---------------------  ---------  ----  -----  ------------------
#16   fix/16-login-redirect  b2/a2 ✓    #101  pass   해결 — merge 후보
#21   feat/21-search-filter  b1/a1 ✓    #102  pass   해결 — merge 후보
#53   fix/53-n-plus-one      b1/a1 ✓    #103  pass   해결 — merge 후보
#64   feat/64-export-csv     b0/a1 ✗    #104  pass   보류 — before 없음
```

`resolved: false` 인 것은 후보에서 뺀다. 사유를 반드시 남긴다. 사용자가 "그래도 넣자"고 하면 넣되, 계획 문서에 예외임을 기록한다.

## 4. 충돌 후보 파악

`overlapsWith` 가 비어 있지 않은 브랜치들은 merge 순서가 결과를 바꿀 수 있다.

```text
fix/16-login-redirect  ↔  feat/21-search-filter   (src/shared/api.ts)
```

이건 "같은 파일을 건드렸다"는 사실일 뿐 실제 충돌은 아니다. 실제 충돌 여부는 merge 를 해봐야 안다. 계획 단계에서 순서를 정하는 재료로만 쓴다.

일반적으로 **변경 파일이 적은 것부터** merge 한다. 충돌이 나도 범위가 좁아 원인을 찾기 쉽다.

## 5. 이미 닫힌 이슈 / 이미 merge 된 PR

- `issueState: CLOSED` 인데 워크트리가 남아 있으면 정리 대상이다. merge 하지 않고 7단계에서 워크트리만 제거할지 묻는다.
- `pr.state: MERGED` 면 이미 통합된 것이다. 워크트리 정리 대상으로만 넘긴다.
- `pr: null` 인데 증거는 충분하면 `issue-end` 로 PR 을 먼저 만들라고 안내한다. 이 스킬이 PR 을 만들지는 않는다.

## 6. 사용자 확인

후보 목록을 확정하기 전에 한 번 보여주고 승인받는다. `excludedCount` 가 0 이 아니면 무엇을 자동으로 걸렀는지도 함께 보여준다.

```text
후보   #16 #21 #53
제외   3개 — 기본 브랜치보다 앞선 커밋이 없어 합칠 것이 없습니다

질문: issue-merge 3단계(merge 후보 확정)입니다.
      아래 <n>개를 이번 통합 대상으로 잡았습니다. 진행할까요?
- 이대로 진행 (권장)
- 일부 제외        → 어떤 것을 뺄지 다시 묻는다
- 보류분도 포함     → 증거가 없는 것도 넣는다. 예외로 기록된다
- 중단
```

**후보가 0개면 묻지 않는다.** 합칠 것이 없다는 뜻이므로 그 사실과 제외 사유를 보고하고 끝낸다. 없는 대상에 대해 계획을 세우거나 서브에이전트를 띄우지 않는다.
이때도 보고 끝에 `현재 단계 — issue-merge 3단계(merge 후보 확정) · 후보 0건으로 종료` 를 남긴다.
