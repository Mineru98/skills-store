# 질문 · 보고 · 링크 형식 정본

**이 파일이 형식의 유일한 출처다.** SKILL.md 와 다른 reference 는 여기를 참조하고, 형식을 따로 정의하지 않는다.
사용자에게 보이는 모든 출력 — 전이 보고, 질문, 문제 보고, 마무리 요약 — 이 여기 규칙을 따른다.

# 1. 단계 이름 정본

```text
 0  base 전용 워크트리 준비
 1  워크트리 인벤토리 수집
 2  워크트리↔이슈 매핑 확인
 3  증거 기반 해결 여부 판정 → merge 후보 확정
 4  분석 서브에이전트 팬아웃 → plan.md
 5  비판 서브에이전트로 모호성 검토
 6  merge · 통합 테스트
 7  이슈 close · 정리
 8  다음 행동 선택
```

**단계 이름은 이 목록에만 적는다.** TodoWrite 체크리스트도 이 9줄을 그대로 쓴다.
줄여 쓰거나 다르게 표현하지 않는다 — 사용자에게 그대로 노출되는 문자열이라, 두 곳에 다르게 적으면 회차마다 다른 이름이 보인다.

# 2. 현재 단계 밝히기

사용자에게 말을 걸 때는 **지금 어느 스킬의 몇 단계인지** 반드시 함께 적는다.

```text
<스킬 이름> <n>단계(<단계 이름>)

예) issue-merge 6단계(merge · 통합 테스트)
```

`<단계 이름>` 은 1절 정본에서 그대로 가져온다.

## 위치는 분량으로 정한다

```text
5줄 미만   단계를 먼저 말하고, 이어서 할 말을 한다
5줄 이상   할 말을 먼저 하고, 마지막에 `현재 단계 — <표기>` 를 한 줄로 남긴다
```

줄 수는 사용자에게 보이는 본문 기준이다. 질문 블록의 선택지는 세지 않는다.
회차 안에서 대상이 여럿이면 대상 범위도 함께 적는다.

```text
issue-merge 5단계(비판 서브에이전트로 모호성 검토)입니다. 계획을 비판 서브에이전트에 넘기겠습니다.
```

```text
후보 3건을 확정했습니다 — #16 #21 #53.

제외 사유와 충돌 후보를 정리했습니다.
통합 순서는 계획에 남겼습니다.
검토가 끝나면 merge 승인을 묻겠습니다.

현재 단계 — issue-merge 3단계(증거 기반 해결 여부 판정 → merge 후보 확정)
```

```text
현재 단계 — issue-merge 6단계(merge · 통합 테스트) · #16 #21 #53 중 #21 처리 중
```

# 3. 질문 블록

**텍스트가 정본이고 `AskUserQuestion` 은 그 위에 얹는 UI 다.**
런타임이 무엇이든 아래 블록을 **먼저 그대로 출력한다.** 그래야 두 런타임에서 화면이 같아진다.

## 형식

```text
질문 — issue-merge 6단계(merge · 통합 테스트)
아래 순서로 3개를 merge 할까요?

1. 이대로 진행 (권장)   계획의 순서대로 #53 → #16 → #21 을 merge 합니다
2. 순서 조정            원하는 순서를 직접 알려주세요
3. 일부만 merge         뺄 대상을 직접 알려주세요
4. 중단                 여기서 멈춥니다. 이미 merge 된 것은 그대로 남습니다

번호로 답해 주세요.
```

## 고정 규칙

```text
머리표기   `질문 — <스킬> <n>단계(<단계 이름>)` 한 종류뿐. `질문:` 도 `질문   ` 도 쓰지 않는다
질문 문장   머리표기 바로 다음 줄에 한 문장. 물음표로 끝낸다
선택지     번호 마커만 쓴다. `-` 불릿은 쓰지 않는다
권장안     반드시 1번. 라벨 뒤에 ` (권장)` 을 붙인다
개수       2~4개
설명       각 선택지 오른쪽에 그 선택의 결과를 한 줄로. 라벨만 두지 않는다
꼬리말     `번호로 답해 주세요.` 한 줄
```

- 한 번에 **하나의 결정만** 묻는다. 여러 승인을 묶지 않는다.
- 이미 확정된 것은 다시 묻지 않는다.
- 블록 앞뒤에 같은 내용을 산문으로 되풀이하지 않는다. 판단 재료는 블록 **앞**에 두고, 블록 뒤에는 아무것도 쓰지 않는다.

## 자유 입력이 필요할 때

값을 직접 받아야 하는 선택지는 **설명에 `직접 알려주세요` 를 적는다.**
`Other 로 입력받는다` 라고 쓰지 않는다 — `Other` 는 `AskUserQuestion` 의 UI 요소라, 툴이 없는 런타임에서는 가리키는 것이 사라진다.

```text
좋은 예   2. 순서 조정   원하는 순서를 직접 알려주세요
나쁜 예   2. 순서 조정   Other 로 순서를 입력받는다
```

## 런타임과 폴백

실행 계열은 SKILL.md 의 `# 스크립트 경로` 에서 이미 판별했다. 그 결과를 그대로 쓴다.

```text
<skill> 이 .claude/ 밑   블록을 출력한 뒤, 같은 라벨·같은 순서로 AskUserQuestion 을 이어 호출한다
<skill> 이 .codex/ 밑    블록만 출력하고 사용자의 답을 기다린다
```

- `.codex/` 계열에는 `AskUserQuestion` 이 없다. **호출을 시도하지 않는다.**
  Codex CLI 와 그 위의 워크플로우 레이어(oh-my-codex 등)가 모두 여기 해당한다.
- `.claude/` 계열에서 호출이 실패하면 **이미 출력한 블록으로 진행한다.** 재호출하지 않는다.
- 어느 경우에도 같은 질문을 형식만 바꿔 다시 던지지 않는다.

`AskUserQuestion` 을 쓸 때는 블록과 어긋나지 않게 한다.

```text
라벨    블록의 라벨을 그대로. `(권장)` 표시도 그대로 남긴다
순서    블록과 같은 순서
설명    블록의 설명 문장을 그대로
본문    머리표기 + 질문 문장. 선택지에 단계 표기를 반복하지 않는다
```

## 답변 해석

번호로 답하는 것을 기본으로 보되, 아래는 모두 같은 선택으로 받는다.

```text
1번을 뜻하는 것   `1`  `1번`  `일번`  `첫번째`  `권장`  라벨의 일부 문자열
```

- 여러 선택지에 걸리거나 어느 것도 아니면 되묻는다. 이때 **같은 블록을 그대로 재출력한다.** 문장을 새로 짓지 않는다.
- 자유 입력 선택지를 골랐으면 값을 받는다. 값이 오지 않았으면 그 값만 한 문장으로 묻는다.

# 4. 문제 보고 형식

무언가 막히거나 어긋났을 때는 아래 다섯 줄 순서를 그대로 지킨다. 순서를 바꾸거나 건너뛰지 않는다.

```text
1. 상황      지금 어디까지 왔고 무엇을 하려던 중인지
2. 문제      무엇이 잘못됐는지
3. 멀쩡한 것  무엇은 문제가 없는지 (사용자가 피해 범위를 알아야 한다)
4. 원인      왜 그렇게 됐는지 (아는 만큼만. 모르면 모른다고 쓴다)
5. 선택      3절의 질문 블록
```

**쉬운 말로 쓴다.** 전문 용어는 꼭 필요할 때만 쓰고, 쓸 때는 바로 옆에 풀어 준다.

```text
나쁜 예   detached HEAD 상태에서 rebase 충돌로 인해 워크트리가 dirty 합니다.
좋은 예   지금 워크트리(이슈 하나를 위해 따로 만든 작업 폴더)에 저장 안 된 변경이 남아 있습니다.
```

**"문제 없는 것"을 반드시 적는다.** 사용자는 어디까지 망가졌는지를 가장 먼저 알고 싶어 한다.

```text
문제      증거 이미지를 기본 브랜치에 올리지 못했습니다.
멀쩡한 것  코드 변경과 커밋은 그대로 남아 있습니다. 이슈도 그대로입니다.
```

**마지막은 항상 질문이다.** 사용자가 무엇을 정해야 하는지 모른 채 끝내지 않는다.

## 예시

```text
상황      이슈 #59 의 코드 변경과 커밋까지 끝냈고, 증거를 기본 브랜치에 올리는 중이었습니다.
문제      기본 브랜치가 보호되어 있어 올리지 못했습니다.
멀쩡한 것  코드 변경, 커밋, 작업 브랜치 push 는 모두 끝났습니다. 잃은 것은 없습니다.
원인      저장소 설정에서 main 브랜치에 직접 push 를 막아 둔 것으로 보입니다.

질문 — issue-merge 6단계(merge · 통합 테스트)
증거를 어디에 올릴까요?

1. 별도 브랜치에 올리기 (권장)   evidence/issue-59 브랜치를 만들어 올립니다. 이슈의 이미지는 정상 표시됩니다
2. 이미지를 직접 첨부            이슈 웹 페이지에 이미지를 끌어다 놓습니다. 손이 한 번 더 갑니다
3. 증거 없이 진행                이미지 없이 글로만 남깁니다. 나중에 확인이 어려워집니다

번호로 답해 주세요.
```

# 5. 링크와 경로 쓰는 법

## 이슈 · PR · 코멘트는 항상 클릭되게

맨 URL 을 그대로 붙이거나 번호만 적지 않는다. `[설명](링크)` 형식으로 쓴다.

```text
나쁜 예   이슈    #59 탭 활성 상태 초기화
          코멘트  https://github.com/owner/repo/issues/59#issuecomment-123

좋은 예   이슈    [#59 탭 활성 상태 초기화](https://github.com/owner/repo/issues/59)
          PR      [#103 fix(tab): 활성 상태 유지](https://github.com/owner/repo/pull/103)
          코멘트  [리포트 보기](https://github.com/owner/repo/issues/59#issuecomment-123)
```

주소는 이미 손에 들어온다. 직접 조립하지 않는다.

```text
gh issue view <n> --json url          이슈 주소
gh pr view <n> --json url             PR 주소
gh issue comment ... 의 출력           방금 단 코멘트 주소
issue-merge inventory 출력의 issueUrl / pr.url
```

저장소를 식별하지 못해 주소를 만들 수 없으면 **번호만 적고** 그 사실을 한 줄 남긴다. 없는 링크를 지어내지 않는다.

## 워크트리 경로는 배치에 맞는 형태로

`ctrl+클릭` 으로 열리려면 형태가 배치와 맞아야 한다.

```text
children   저장소 안  → 상대 경로   .issue/worktrees/59-tab-active-state
sibling    저장소 밖  → 절대 경로   /Users/me/work/repo-issue-59
```

sibling 을 상대 경로로 적으면 `../repo-issue-59` 가 되어 **없는 경로로 열린다.** 반대로 children 을 절대 경로로 적으면 쓸데없이 길다.

스크립트가 계산해 둔 값을 그대로 쓴다.

```text
issue-merge.mjs inventory  출력의 worktrees[].display / excluded[].display
```

직접 판단해야 하면 설정이 아니라 **실제 경로**를 본다. `git worktree list` 로 경로를 얻어 저장소 루트 아래면 children, 아니면 sibling 이다.
설정값은 새로 만들 때만 쓰이므로, 이미 있는 워크트리는 예전 설정으로 만들어졌을 수 있다.
