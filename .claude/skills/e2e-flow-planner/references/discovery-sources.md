# 이슈·기획서 탐색 (MCP와 대체 경로)

CUF 후보를 추측이 아니라 근거로 뒷받침하기 위해, "사람들이 실제로 무엇을 중요하게 여기고 무엇이 자주 깨지는지" 신호를 모은다. 이 문서는 어디서 그 신호를 얻는지 정리한다.

## 신호를 어디서 얻나

우선순위 높은 순:

1. **이슈/버그 트래커** — 반복되는 버그, 핫픽스, "장애" 라벨이 붙은 이슈는 곧 회귀 위험 지점이다. 가장 자주 깨진 곳이 가장 보호해야 할 곳일 때가 많다.
2. **기획서·PRD·스펙 문서** — "이 기능의 성공 기준"이 적혀 있다. 성공 기준 = 기대결과의 원천.
3. **코드베이스 라우트·네비게이션** — 사용자가 실제로 지나가는 경로의 골격. 메인 메뉴/탭에 노출된 플로우는 빈도가 높다.
4. **분석/로그(있으면)** — 트래픽이 몰리는 경로 = 빈도 높음 = P0 후보.

## MCP가 있을 때

사용 가능한 MCP 서버를 먼저 확인한다(이슈 트래커, 문서/위키, 지라/깃헙 류). 그런 MCP가 붙어 있으면 그것으로 이슈·기획서를 조회한다.

탐색할 때 던지는 질문:

- "최근 1~2개 분기에 가장 많이 깨진/핫픽스된 영역은?"
- "장애·인시던트로 이어진 플로우가 있었나?"
- "이 기능(예: 대출 신청)의 기획상 성공 기준과 핵심 분기는?"
- "결제·인증·본인확인처럼 외부 의존이 끼는 단계는 어디인가?"

얻은 근거는 CUF 후보 옆에 출처와 함께 적는다. 예: "CUF-2 대출 신청 — 근거: ISSUE-1421(신청 제출 시 간헐 실패) 3회 재발".

> 어떤 MCP가 붙어 있는지는 세션마다 다르다. 이름을 추측하지 말고, 실제 사용 가능한 도구 목록에서 이슈/문서 계열을 찾아 쓴다. 없으면 아래 대체 경로로 간다.

## MCP가 없을 때 (대체 경로)

MCP가 없어도 계획은 만들 수 있다. 다음 순서로 근거를 모은다.

1. **레포 내 문서 검색** — 기획/스펙이 레포에 있는 경우가 많다.
   ```bash
   # 기획·요구사항·테스트 관련 문서 찾기
   rg -l -i "요구사항|기획|스펙|acceptance|user story|시나리오" --glob '*.md'
   ```
2. **이슈 트래커 CLI** — GitHub면 `gh`.
   ```bash
   # 최근 버그/핫픽스 라벨 이슈 (가장 자주 깨진 곳 = 보호 우선순위)
   gh issue list --label bug --state all --limit 30
   gh issue list --search "결제 OR 인증 OR 신청 in:title" --limit 30
   ```
3. **라우트·네비게이션 골격** — 코드에서 직접.
   ```bash
   # Next.js app/ 라우트(page.tsx) 또는 pages/ 라우트 — page.tsx 는 파일이므로 -t f
   fd -t f 'page.tsx' app pages 2>/dev/null || rg -l "export default function .*Page" app pages
   # 메인 네비게이션/메뉴 정의 (빈도 높은 경로 단서)
   rg -i "nav|menu|route|href" --glob '*.{ts,tsx}' -l
   ```
4. **최근 변경이 잦은 영역** — git 히스토리로 "활발히 바뀌는 = 회귀 위험" 지점 파악.
   ```bash
   git log --since="3 months ago" --name-only --pretty=format: | sort | uniq -c | sort -rn | head -30
   ```

근거를 하나도 못 찾으면, 그 CUF는 "가정"으로 표시하고 계획서의 오픈 질문에 올려 검토자에게 확인받는다.

## 주의

- 이슈 내용에 있는 자격증명·토큰·개인정보를 계획서에 그대로 옮기지 않는다.
- "자주 깨진 곳"과 "중요한 곳"은 보통 겹치지만 항상은 아니다. 최종 우선순위는 cuf-criteria.md의 매출/데이터/신뢰 렌즈로 다시 거른다.
