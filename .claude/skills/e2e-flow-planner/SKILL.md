# E2E Flow Planner

E2E 테스트를 "무엇부터 짤지" 정하는 **Planner** 단계. 산출물은 코드가 아니라, 사람이 검토하는 **마크다운 테스트 계획서**다.

## 이 스킬의 철학 (왜 이렇게 하는가)

모든 것을 테스트하지 않는다. 목적은 **잘못된 수정이 기존 동작을 깨뜨리는 것을 막는 것**이지, 코드가 바뀔 때마다 테스트가 깨지게 만드는 게 아니다. 화면 단위로 빠짐없이 테스트를 깔면 유지보수 부담만 커지고, 정작 중요한 회귀는 놓친다.

그래서 한 질문에서 시작한다: **"가장 중요한 사용자 워크플로우는 무엇인가?"**

여기서 "중요"의 기준은 명확하다. 그 플로우가 실패하면

- **매출이 막히거나** (결제·신청·구독 완료가 안 됨),
- **데이터가 날아가거나** (사용자 입력·거래 기록 유실),
- **신뢰가 깨지는** (본인확인·인증·금액 표시 오류)

부분이다. 이것이 **Critical User Flow(CUF)** 다. 개발자가 "여기까지는 안전하다"고 확신을 얻을 자리를 추려내는 게 이 스킬의 본질이다.

핵심 산출 규율: **코드를 짜기 전에**, 사람이 읽고 "이게 맞는 우선순위가 맞다"고 판단할 수 있는 계획서를 먼저 낸다. **사람 검토 게이트가 이 스킬의 심장**이다. 계획이 승인되기 전에는 테스트 코드로 넘어가지 않는다.

## 무엇을 하지 않는가 (경계)

- 테스트 **코드 작성·실행은 하지 않는다.** 그건 승인된 계획서를 입력으로 받는 별도 단계(Author/Runner)의 일이다.
- 브라우저 탐색에서 **로그인·결제·본인확인을 임의로 끝까지 진행하지 않는다.** 인증 벽을 만나면 거기서 멈추고, 그 지점을 계획서에 "수동 선행조건/모킹 필요"로 기록한다.
- 모든 화면을 빠짐없이 훑지 않는다. CUF 후보를 좁히는 데 필요한 만큼만 탐색한다.

승인된 계획서는 다음 단계로 넘긴다: 코드 구현은 `e2e-test-generator`, 견고화는 `e2e-test-hardener`, 실패 진단은 `e2e-test-healer`. 이 스킬은 그 앞단(무엇을·왜 테스트할지 + 사람 검토)만 책임진다.

## 워크플로우

순서를 지킨다. 각 단계는 "다음 단계로 넘어가도 되는지"를 스스로 확인하는 검증 지점을 갖는다.

### 1. 도메인·범위 파악 → 검증: CUF 후보 3~7개를 한 줄씩 적었다

먼저 이 앱이 사용자에게 약속하는 핵심 가치가 무엇인지 파악한다. 가능한 입력원:

- 사용자가 말한 도메인/기능 설명
- 코드베이스의 라우트·페이지 구조 (Next.js라면 `app/` 또는 `pages/`, 라우트 정의, 네비게이션 메뉴)
- 이슈·기획서 (아래 2단계 MCP 탐색)

후보를 좁힐 때 "매출/데이터/신뢰" 렌즈로 거른다. 자세한 판별 기준과 안티패턴은 `references/cuf-criteria.md` 를 읽는다.

### 2. 이슈·기획서 탐색 (MCP) → 검증: 각 CUF 후보에 근거(이슈/문서/라우트)를 붙였다

사용 가능한 MCP가 있으면 관련 이슈·기획서를 살펴 "사람들이 실제로 무엇을 중요하게 여기고, 무엇이 자주 깨지는지" 신호를 모은다. 어떤 MCP를 어떻게 쓰는지, MCP가 없을 때의 대체 경로(이슈 트래커 CLI, 레포 내 문서 grep)는 `references/discovery-sources.md` 를 읽는다.

근거 없는 CUF는 추측이다. 후보마다 "왜 이게 중요한가"를 라우트/이슈/문서 중 하나로 뒷받침한다.

### 3. 라우트·화면 실제 탐색 (playwright-cli) → 검증: 플로우 단계가 실제 화면과 일치한다

CUF 후보의 실제 화면을 둘러보며 단계(진입 → 입력 → 분기 → 완료)와 화면 전환을 확인한다. 이때 **이미 있는 `playwright-cli` 스킬을 탐색 도구로 그대로 쓴다 — 브라우저 구동 방법을 여기서 다시 설명하지 않는다.** 탐색에 필요한 최소 명령은 다음과 같다.

```bash
playwright-cli open <url>      # 앱 진입
playwright-cli snapshot        # 화면 구조·요소(ref) 확인 → 플로우 단계 추출
playwright-cli goto <url>      # 다음 화면으로 이동하며 단계 따라가기
```

전체 명령·세션·옵션은 `playwright-cli` SKILL.md(`.claude/skills/playwright-cli/SKILL.md`)를 참조한다. 탐색을 계획으로 옮기는 구체 방법(어디서 멈추고, 무엇을 단계로 적을지)은 `references/exploration-with-playwright.md` 를 읽는다.

탐색 중 인증/결제 벽을 만나면 멈추고 그 지점을 "선행조건"으로 기록한다. 자격증명을 화면에서 읽어 입력하지 않는다.

### 4. 계획서 작성 → 검증: 아래 템플릿의 모든 섹션이 채워졌고, 각 플로우에 우선순위·근거·단계·기대결과·선행조건이 있다

`references/test-plan-template.md` 의 구조를 그대로 써서 `e2e-test-plan.md`(또는 사용자가 지정한 경로)에 작성한다. 시나리오는 사람이 읽고 검토할 수 있게 산문 단계로 적는다 — 여기서는 셀렉터/코드를 넣지 않는다(계획서는 "무엇을"이고, 셀렉터는 "어떻게"라서 Author 단계 소관).

### 5. 사람 검토 게이트 → 검증: 사용자가 우선순위/범위에 명시적으로 동의했다

계획서를 사용자에게 제시하고 검토를 요청한다. 이 게이트를 건너뛰지 않는다. 예시 문구:

```text
E2E 테스트 계획서 초안을 e2e-test-plan.md 에 작성했습니다.
Critical User Flow를 우선순위 순으로 N개 추렸습니다.

검토해주실 점:
1. 우선순위가 맞나요? (실패 시 매출/데이터/신뢰 영향 기준)
2. 빠진 핵심 플로우가 있나요?
3. 과한(=테스트 가치 낮은) 플로우가 섞여 있나요?

승인해주시면 이 계획서를 기반으로 테스트 작성 단계로 넘어갑니다.
```

사용자 피드백을 반영해 계획서를 고친다. 승인 전에는 테스트 코드 단계로 넘어가지 않는다.

## 산출물 한눈에

- 파일 하나: `e2e-test-plan.md` (사람이 검토·승인하는 마크다운).
- 내용: CUF 목록(우선순위·근거), 플로우별 시나리오(단계/기대결과/선행조건), 비대상(Out of scope) 명시, 가정·오픈 질문.
- **셀렉터·테스트 코드 없음.** 그건 승인 후 다음 단계.

## 도메인 적용 예시 (네이버페이 대출 류)

"무엇을 CUF로 뽑는가"의 감을 잡기 위한 예시다. 그대로 베끼지 말고, 대상 앱의 매출/데이터/신뢰 지점으로 치환한다.

- **대출 한도조회 플로우**: 홈 진입 → 약관 동의 → 휴대폰 인증·본인확인 → 한도/금리 결과 조회. (실패 시 = 핵심 가치 자체가 동작 안 함 → 신뢰 붕괴)
- **대출 신청 플로우**: 신청 가능 상품 목록 → 상품 상세 → 신청 완료. (실패 시 = 매출 직결)

이 두 가지가 "가장 중요한 워크플로우"다. 마이페이지 배너 노출 여부 같은 건 CUF가 아니다 — 깨져도 매출/데이터/신뢰에 직접 타격이 없다.

## 참조 파일 (필요할 때 읽기)

- `references/cuf-criteria.md` — CUF 판별 기준, 매출/데이터/신뢰 렌즈, 흔한 안티패턴(과잉/과소 선정).
- `references/discovery-sources.md` — 이슈/기획서 MCP 탐색 방법과 MCP 부재 시 대체 경로.
- `references/exploration-with-playwright.md` — playwright-cli로 탐색해 플로우 단계를 뽑아 계획으로 옮기는 법(인증 벽 처리 포함).
- `references/test-plan-template.md` — 계획서 마크다운 템플릿(이 형식을 그대로 사용).
