# 요청 분해

한 메시지에 작업이 여러 개 담겨 오는 일이 흔하다. "필터도 넣고, 목록 비는 것도 고치고, 옛날 export 스크립트도 지워줘."
이걸 이슈 하나에 뭉치면 `issue-start` 가 브랜치 하나로 세 가지를 건드리고, `issue-end` 의 증거가 뭘 증명하는지 흐려지고, `issue-merge` 가 되돌릴 단위를 잃는다.

**이슈 하나 = 워크트리 하나 = PR 하나** 가 뒤 단계의 전제다. 분해는 그 전제를 지키기 위한 것이지, 잘게 쪼개는 것 자체가 목적이 아니다.

## 독립성 테스트

네 항목을 **모두** 만족할 때만 쪼갠다.

```text
1. 각각 따로 PR 로 머지해도 말이 되는가
2. 완료 기준이 서로 겹치지 않는가
3. 하나가 취소돼도 나머지가 성립하는가
4. 라벨 성격이 갈리는가 (bug / enhancement / chore 가 섞임)
```

하나라도 아니면 **단일 이슈 + 완료 기준 체크리스트** 로 간다. 억지 분할이 뭉친 이슈보다 나쁘다.

### 쪼개는 예

```text
"대시보드에 기간 필터 넣고, 주문 목록이 가끔 비는 것도 고치고,
 안 쓰는 export 스크립트 지워줘"

→ #A 대시보드 기간 필터 추가        enhancement
  #B 주문 목록 빈 렌더링 수정        bug
  #C 레거시 export 스크립트 제거      chore

1 각각 따로 머지 가능        ✓
2 완료 기준 안 겹침          ✓
3 하나 취소돼도 나머지 성립   ✓
4 라벨 셋 다 다름            ✓
```

### 쪼개지 않는 예

```text
"로그인 폼 반응형 깨진 거 고쳐줘. 모바일에서 버튼 잘리고
 태블릿에서는 라벨이 겹쳐"

→ 이슈 1개. 완료 기준을 체크리스트로 나눈다.
  - [ ] 375px 에서 제출 버튼이 잘리지 않는다
  - [ ] 768px 에서 라벨이 입력란과 겹치지 않는다

2 완료 기준이 "로그인 폼 반응형" 하나로 수렴   ✗
3 버튼만 고치고 라벨을 남기면 이슈가 안 닫힘    ✗
```

```text
"API 응답에 createdAt 추가하고, 그거 목록에 표시해줘"

→ 이슈 1개. 계약 변경과 소비가 한 몸이다.
3 API 만 바꾸고 화면을 안 바꾸면 아무 효과가 없다   ✗
```

## 상한

**5개.** 넘으면 AskUserQuestion 으로 한 번 묻는다.

```text
질문: 요청에서 독립 작업 7건을 찾았습니다. 이슈 7개는 관리 비용이 큽니다.
- 관련된 것끼리 묶어 3~4개로 (권장)   → 묶는 기준을 제시하고 다시 확인
- 7개 그대로 등록
- 지금 급한 것만 골라 등록            → 번호를 받아 그것만
```

## 2단계 승인

초안 N 개를 한 번에 던지면 사용자가 검토를 포기한다. **분할안을 먼저 확정하고** 초안을 쓴다.

### 1단계 — 분할안

제목과 한 줄 요약, 예상 라벨만 보여준다. 본문은 아직 쓰지 않는다.

```text
요청을 이슈 3건으로 나눴습니다.

1. 대시보드 기간 필터 추가        enhancement
   현재 전체 기간 고정 → 시작일·종료일 선택 UI 추가

2. 주문 목록 빈 렌더링 수정        bug
   새로고침 직후 목록이 비어 보였다가 채워지는 현상

3. 레거시 export 스크립트 제거      chore
   scripts/export-legacy.mjs — 6개월간 호출 흔적 없음
```

AskUserQuestion 으로 받는다.

```text
승인      이 구성으로 초안 작성
병합      어느 것과 어느 것을 합칠지 받아 다시 제시
분리      한 항목을 더 쪼갤지 받아 다시 제시
취소      등록하지 않고 종료
```

### 2단계 — 초안 일괄

승인된 항목마다 `issue-draft.md` 의 틀을 채워 **전문을 한 번에** 보여준다.

```text
승인      전부 이대로 등록
일부 수정  번호를 받아 그 항목만 다시 초안 제시
취소      등록하지 않고 종료
```

## 분해하지 않는 경우

다음은 애초에 이 절차를 타지 않는다.

- 요청에 작업이 하나뿐 → 바로 초안 1건. 분할안 단계를 건너뛴다.
- 사용자가 `/issue-create` 에 인자로 이슈 하나를 명시 → 그대로 1건.

## 항목별 처리

분할안이 확정되면 **항목마다** 다음을 따로 돈다.

```text
중복 검사   node <skill>/scripts/issue-create.mjs search "<항목 키워드>"
성격 판정   frontend / backend / both
초안 작성   references/issue-draft.md
```

중복이 걸린 항목은 **그 항목만 빼고** 나머지를 진행한다. 전체를 중단하지 않는다.
빠진 항목은 마무리 보고의 `건너뜀` 줄에 이유와 함께 남긴다.

```text
건너뜀    "알림 배지" — #48 과 중복
```

## 형제 이슈의 흔적

분해된 이슈는 서로를 모른다. `issue-start` 의 대조 분석이 맥락을 잃지 않도록,
`--request-file` 에 **원본 요청 전문 + 이 이슈가 맡는 범위** 를 함께 담는다. 세부는 `issue-draft.md`.

이슈 본문에 `#N` 상호 참조를 넣지 않는다. 등록 시점에는 형제 번호를 모르고,
등록 후 본문을 고치는 것은 이 스킬의 권한 밖이다.
