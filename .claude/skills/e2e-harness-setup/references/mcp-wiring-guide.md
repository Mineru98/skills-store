# MCP 서버 배선 가이드

> 단계 4 의 깊이 문서. 목표: 테스트가 검증해야 할 "기대 동작"의 **원천 맥락**(기획·디자인·이슈·PR)에 에이전트가 직접 닿게 한다.

## 왜 연결하나

E2E 테스트는 "이 화면이 이렇게 동작해야 한다"를 검증한다. 그 "이렇게"는 코드가 아니라 **사내에서 이전에 논의된 곳**에 있다: 기획서, 디자인 시안, 이슈 토론, PR 리뷰. 이게 연결돼 있지 않으면 에이전트는 기대 동작을 추측하거나 사람에게 매번 묻는다. MCP 로 원천에 닿으면 에이전트가 스스로 "기획서엔 이 케이스가 뭐라고 돼 있지?"를 확인한다.

이건 단계 1~3 이 코드/문서에 박제한 맥락의 연장선이다. 1~3 은 *우리가 글로 쓴* 맥락, 4 는 *이미 다른 도구에 쌓여 있는* 맥락을 연결한다.

## 무엇을 연결하나 (우선순위)

테스트 컨텍스트에 기여하는 순서로:

1. **이슈/작업 트래커** — 기대 동작·수용 기준(acceptance criteria)·버그 재현 조건의 1차 출처. (예: 깃 호스팅 이슈, Jira 류)
2. **소스 호스팅(PR/코드 리뷰)** — "왜 이렇게 바뀌었나", 회귀 위험, 리뷰에서 합의된 엣지 케이스. (예: GitHub MCP)
3. **기획/문서** — 스펙 문서, 위키. 플로우의 의도와 비기능 요구.
4. **디자인 도구** — 화면 상태·빈 상태·에러 상태 정의(예: Figma류). 시각 단언의 근거.

전부 한 번에 붙일 필요는 없다. **단계 1~2 에서 식별한 핵심 플로우를 검증하는 데 필요한 것부터** 연결한다.

## 실제 설치는 mcp-setup 스킬에 위임

MCP 서버를 고르고 자격증명을 넣고 `.mcp.json`/설정에 등록하는 구체 절차는 이 저장소의 **`mcp-setup`** 스킬이 담당한다. 여기서 그 절차를 복제하지 않는다. 이 가이드는 **무엇을 왜 연결할지**의 결정만 다룬다.

연결 후 산출물은 보통:
- 프로젝트 루트 `.mcp.json`(또는 동등 설정)에 서버 등록.
- 자격증명은 환경변수/시크릿으로. **토큰을 설정 파일에 평문 저장 금지**, 커밋 금지.

## SSOT 에 무엇을 적나

연결 자체보다 **연결의 의미를 SSOT 에 적는 것**이 중요하다. 그래야 다음 에이전트가 "이 컨텍스트는 어디서 오나"를 안다. SSOT 의 해당 섹션 예:

```markdown
## 컨텍스트 소스 (MCP)
- 이슈/수용기준: <트래커 MCP> — 기대 동작과 AC 는 여기서 확인.
- PR/리뷰 합의: <GitHub MCP> — 엣지 케이스·회귀 위험.
- 기획 문서: <문서 MCP> — 플로우 의도.
- 디자인 상태: <Figma MCP> — 빈/에러 상태 정의.

미연결 항목과 이유:
- 디자인 MCP 미연결 — 현재 시각 회귀는 범위 밖(DR-00X 참조).
```

**미연결도 결정이다.** 안 붙였으면 왜 안 붙였는지 적는다. 그래야 에이전트가 없는 도구를 찾아 헤매지 않는다.

## 안티패턴

- 토큰을 `.mcp.json` 에 평문으로 박고 커밋 — 유출 사고. 환경변수/시크릿으로.
- 닥치는 대로 다 연결 — 컨텍스트 노이즈만 늘고 핵심 플로우 검증엔 안 쓰인다. 플로우가 요구하는 것부터.
- 연결만 하고 SSOT 에 안 적음 — 다음 세션 에이전트는 그 도구의 존재·용도를 모른다.

## 마무리 점검

- 핵심 플로우(단계 1~2)의 기대 동작을 에이전트가 **사람에게 안 묻고** MCP 로 확인할 수 있나?
- 연결/미연결이 SSOT 에 기록됐나?
- 자격증명이 안전하게(환경변수, 비커밋) 처리됐나?
