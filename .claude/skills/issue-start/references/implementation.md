# 구현과 커밋

`plan.md` 의 작업 계획을 실제로 수행하는 단계다. before 캡처가 끝난 뒤에 시작한다.

## 1. 순서를 지킨다

계획의 변경 목록을 위에서부터 처리한다. 중간에 계획과 다른 판단이 필요해지면 **`plan.md` 를 먼저 고치고** 진행한다. 계획과 구현이 어긋난 채로 끝나면 `issue-end` 가 증거를 대조할 기준을 잃는다.

## 2. 범위를 지킨다

- 이슈에 적힌 것만 고친다. 지나가다 발견한 다른 문제는 고치지 말고 마무리 보고에 한 줄로 남긴다.
- 주변 코드의 포맷·주석·네이밍을 "개선"하지 않는다. 증거 diff 가 지저분해지면 리뷰가 불가능해진다.
- 내 변경이 만든 미사용 import·변수는 지운다. 원래 있던 죽은 코드는 건드리지 않는다.

## 3. 검증

`plan.md` 4번의 검증 방법을 그대로 돌린다. 저장소에 실제로 있는 스크립트를 쓴다.

```bash
cat package.json | grep -A 20 '"scripts"'   # 실제 명령 확인
```

프론트엔드면 lint → type-check → build 순서를 지킨다. 백엔드면 계획에 적은 측정 명령을 돌려 after 수치를 만든다.

**검증이 실패하면 커밋하지 않는다.** 실패한 채로 넘어가면 증거가 거짓이 된다.

## 4. 커밋

이 단계만 사용자에게 묻지 않는다. 그 대신 안전장치를 먼저 통과해야 한다.

```bash
node <skill>/scripts/issue-start.mjs guard
```

3중 가드를 전부 만족해야 `ok: true` 다.

```text
isLinkedWorktree      링크된 워크트리인가          (주 체크아웃이면 실패)
notOnBaseBranch       기본 브랜치가 아닌가          (main/master 면 실패)
branchHasIssueNumber  브랜치에 이슈 번호가 있는가   (임시 브랜치면 실패)
```

하나라도 실패하면 exit 3 이고 `reason` 이 나온다. 이때는 **커밋하지 말고** 이유를 보고한 뒤 사용자 확인을 받는다.

가드가 통과하면 바로 커밋한다.

```bash
git add -A
git commit -m "<type>(<scope>): <한 줄 요약>

Refs #{issue_number}"
```

- 커밋 메시지는 저장소의 기존 형식을 따른다. `git log --oneline -20` 으로 확인한다.
- **증거 파일은 이 커밋에 넣지 않는다.** 구현 커밋과 증거 커밋을 분리해야 리뷰에서 diff 가 읽힌다. 증거는 9~10단계에서 따로 커밋한다.
- 변경이 여러 관심사에 걸치면 커밋을 나눈다.

## 5. 왜 묻지 않는가

`issue-start` 는 워크트리 안에서만 동작하고, 그 워크트리는 이 스킬이 방금 이슈 번호로 만든 것이다. 되돌리기도 쉽다(`git reset`, 워크트리 삭제). 매 커밋마다 확인을 받으면 여러 이슈를 동시에 굴리는 흐름이 끊긴다.

반대로 가드가 하나라도 깨졌다는 것은 **여기가 그 워크트리가 아니라는 뜻**이므로, 그때는 예외 없이 확인을 받는다. 이것이 무확인 커밋을 허용하는 유일한 근거다.
